# 그림으로 설명하는 아티팩트

목표는 **읽지 않고 봐도 이해되는 페이지**다. 글은 그림을 읽는 법만 알려주고, 내용은 그림이 전한다.
모양(색감, 왼쪽 요약 리스트)의 기준: [naquiz STOMP 가이드](https://claude.ai/artifact/WEuWeG2HXZASFHJriTs9te)

## 1. 사실 모으기 (추측하지 않는다)
- 설명할 대상($ARGUMENTS 또는 대화 주제)의 실제 코드·문서를 읽는다. 클래스·메서드·메시지·상태 이름은 코드에 있는 그대로 쓴다.
- 규칙은 `docs/기획.md`, `docs/DOMAIN.md`, `docs/API.md`, `core/docs/`에서 확인한다. 코드와 문서가 다르면 페이지에 쓰지 말고 사용자에게 먼저 알린다.
- 아직 없는 기능, 알려진 문제(리뷰 Warning 등)는 따로 모아 마지막 섹션에 둔다.

## 2. 섹션 정하기
큰 그림에서 세부로 들어가는 순서로 3~5개 섹션을 고른다. **섹션마다 그림 하나**가 원칙이다. 필요한 것만 쓴다.
섹션에는 `01`부터 번호를 붙이고, 왼쪽 목차(요약 리스트)에 섹션마다 한 줄씩 넣는다. 목차 항목은 섹션 이름 + 한 줄 요약(15자 안팎)이고 `href`는 섹션 `id`다.

| 섹션 | 그림 | 언제 |
|---|---|---|
| 큰 흐름 | 흐름도: 노드 + 화살표 + 되돌아가는 고리 + 조건 마름모 | 상태가 순환하거나 분기하는 흐름(게임 한 판, 요청 처리 전체) |
| 한 동작이 처리되는 길 | 순서도: 레인(클래스·레이어) + 번호 화살표 + 락/트랜잭션 영역 | 요청 하나가 여러 레이어·스레드를 지나는 과정 |
| 주고받는 메시지 | 표: 방향 칩 + destination/type + 언제 + 담는 것 | API·STOMP 메시지가 3개 이상일 때 |
| 상태가 바뀌는 방식 | 상태 칩 사슬 | 엔티티 상태(enum) 전이 |
| 아직 없는 것 | 짧은 목록 | 범위 밖·남은 문제 |

## 3. 글 쓰는 규칙
- 섹션 설명은 **2문장 이하**. 그림을 읽는 법이나 핵심 규칙 하나만 쓴다.
- 그림 안 글자는 짧게: 노드 제목 2~6자, 보조 설명 한 줄. 긴 설명은 그림 아래 `note` 카드(제목 + 1~2문장)로 뺀다. 카드는 섹션당 2~5개.
- 메시지·이벤트·enum·클래스 이름은 `mono`(그림) 또는 `<code>`(글)로 쓴다.
- 페이지의 문장은 **존댓말(합니다체)**로 쓴다. 예: "정답이 나오면 다음 라운드를 엽니다." 그림 안 짧은 이름표(노드 제목, 화살표 라벨)는 명사형으로 둔다.
- 짧은 문장으로 쓰고 이모지, 과장, "~할 수 있습니다" 같은 군더더기는 뺀다.
- 섹션 번호 말고 그림 안 번호(1, 2, 3…)는 실제 순서가 있을 때만 붙인다.

## 4. 만들기
1. Artifact 도구 규칙대로 새 아티팩트는 `quickstart`(intent `other`)를 먼저 부른다.
2. [template.html](template.html)을 scratchpad로 복사해 시작한다. `<style>`의 토큰·클래스는 바꾸지 않고 목차와 본문만 채운다. 그래야 팀 아티팩트들이 같은 모양을 유지한다.
   - 구조: 왼쪽 `nav.toc`(요약 리스트, 좁은 화면에서는 위로 올라감) + 오른쪽 `main`(hero 헤더 → 섹션들).
   - 색은 토큰만 쓴다(라이트·다크 둘 다 정의돼 있다). SVG 요소도 클래스(`node`, `edge-accent`, `mono` 등)로만 칠한다.
   - 노드: `node`(보통), `node-accent`(핵심·새로 생긴 단계), `node-gold`(조건·신호 같은 강조). 화살표: `edge`, `edge-accent`(메시지가 나가는 길), `edge-gold`, 점선은 `dashed`(응답·되돌아옴). 메시지·이벤트 이름(`mono`)은 호박색으로 그려진다.
   - SVG는 `viewBox` 너비 960~1000으로 그리고, 좁은 화면은 `.figure`가 가로 스크롤한다.
3. 그림을 다 그린 뒤 겹침을 점검한다. 글자 너비는 한글 12.5px 기준 한 글자 약 12px로 어림한다. 화살표 위 글자가 다른 생명선·노드와 겹치면 옮긴다.
4. `<title>`은 "naquiz <주제>" 같은 짧은 이름으로 쓴다. 게시할 때 `description`에는 한 문장 요약, `icon`에는 한 단어(flow, lock, chat 등)를 넣는다.
5. **마지막으로 윤문한다.** 게시 직전에 `humanize-korean:humanize-korean` 스킬로 페이지의 문장(lead, 섹션 설명, 카드, keypoint, 목차 요약, 표의 설명 칸, 남은 것 목록)을 다듬는다.
   - 문장만 뽑아 넘기고, 다듬은 문장을 같은 자리에 되돌려 넣는다. 태그·속성·SVG 좌표는 건드리지 않는다.
   - 코드 이름, 메시지 type, destination, 숫자, 그림 안 이름표는 바꾸지 않는다. 존댓말(합니다체)은 유지한다.
   - 뜻이 바뀐 문장이 있으면 원래 문장으로 되돌린다.

## 5. 게시 후
- 링크를 사용자에게 주고, 비공개라 팀원이 보려면 아티팩트의 Share로 공유해야 한다고 알린다.
- 작업 브랜치의 개발일지 "한 일"에 아티팩트 링크를 남긴다(예: `흐름 그림 아티팩트: [이름](링크)`). PR과 관련 있으면 PR 본문 "무엇을"에도 건다.
- 코드가 바뀌어 그림이 틀려지면 같은 파일 경로로 다시 게시해 같은 링크를 유지한다. 다른 대화에서 고칠 때는 `Artifact` 도구로 먼저 읽고(`action: read`) 그 버전 위에서 고친다.

## PR에서 쓸 때 (/pre-pr)
- `/pre-pr` 1단계에서 만들지 묻고, 만들기로 하면 2단계에서 `explain-drafter` 에이전트가 이 문서의 규칙과 `template.html`로 초안을 쓴다. 윤문(4단계 5번)과 게시는 메인 대화가 한다.
- 관점은 "이번 PR로 무엇이 어떻게 동작하게 됐는가"다. 새로 생기거나 바뀐 부분은 `node-accent`·`edge-accent`로 구분한다.
- 브랜치마다 아티팩트 하나를 쓴다. 초안은 `.git/claude-explain/<브랜치>.html`, 링크는 `.git/claude-explain/<브랜치>.url`에 남기고(`/`는 `__`), 다시 `/pre-pr`을 돌리면 같은 링크로 갱신한다.
