## 결정한 것
- **서버는 멀티모듈, 앱 3개**: 공통(엔티티·저장소·외부 API 클라이언트)은 core-domain에 두고 게임·관리자 API·데일리 크롤링 배치를 따로 배포한다. global 모듈과 별도 웹 모듈은 두지 않고, 웹 공통은 game-api에 둔다. 규모만 보면 게임 서버에 합쳐도 되지만 크롤링 장애·배포가 게임과 묶이지 않게 나눴다. → [모듈 구조](../../core/docs/ARCHITECTURE.md#모듈-구조)
- **단서는 힌트와 별개 엔티티**: 단서는 차례 참가자가 여는 영화 정보이고, 정답 힌트는 모든 단서가 열린 뒤 정답 형태를 보여준다. 공개 주체와 조건이 달라서 분리했다. 단서는 공개한 참가자 ID가 필수이고, 힌트에는 이 속성이 없다. → [3-2. 게임 애그리거트](../DOMAIN.md#3-2-게임-애그리거트)
- **관리자 페이지 도메인**: 관리자·크롤링 실행 애그리거트, 문제 검수 상태, 오류 신고 처리자, 힌트 통계 조회 모델을 추가했다. 데일리 크롤링은 노래만 하고, 새 문제는 승인 전 출제하지 않는다. 초기 데이터로 적재한 문제는 승인 상태로 시작한다. 정답은 검수 상태와 관계없이 고칠 수 있고, 정답 오류 신고에는 신고자가 올바른 정답(`suggestedAnswer`)을 적을 수 있다. 힌트 통계는 정답 힌트·단서를 포함하고 자동 공개 힌트는 뺀다. → [3-7. 관리자](../DOMAIN.md#3-7-관리자-애그리거트), [3-8. 크롤링 실행](../DOMAIN.md#3-8-크롤링-실행-애그리거트), [3-10. 힌트 통계](../DOMAIN.md#3-10-힌트-통계-백오피스-조회-모델)

- **에러 코드는 `ErrorCode` enum 하나, `HttpStatus`를 가진다**: 도메인별 ErrorCode 타입을 만들지 않는다. domain이 `ErrorCode`를 통해 간접적으로 Web에 의존하는 것은 허용했다(HTTP 매핑을 handler로 빼는 대안보다 단순함을 택함). → [ErrorCode 규칙](../../core/docs/EXCEPTION.md#errorcode-규칙), [Domain 작성 규칙](../../core/docs/ARCHITECTURE.md#domain-작성-규칙)
- **레이어·도메인 참조**: domain은 presentation을 제외한 모든 레이어가 참조하는 핵심 모델로 두고, 다른 도메인은 그 도메인의 implement를 직접 주입받는다(포트·어댑터는 규모에 비해 과해서 버림). implement는 `service/implement` 하위 패키지. → [의존성 방향](../../core/docs/ARCHITECTURE.md#의존성-방향)
- **이벤트 발행기는 하나**: 외부 큐가 생기기 전까지 인프로세스 발행기 하나만 두고 어댑터 구조는 미뤘다. → [이벤트 발행 규약](../../core/docs/ARCHITECTURE.md#이벤트-발행-규약)
- **실시간(STOMP) 규칙**: 메시지 경로 예외는 `@MessageExceptionHandler`로 보낸 참가자에게만 보낸다. 채팅·정답 제출 원문은 로그에 남기지 않는다. → [STOMP 에러 처리](../../core/docs/EXCEPTION.md#실시간-메시지stomp-에러-처리), [실시간 메시지 로그](../../core/docs/LOG.md#실시간-메시지-로그)
- **테스트 기준**: 단순 CRUD·위임·프레임워크 동작은 테스트하지 않고, 테스트를 쓰기 전에 검증할 행위 목록을 먼저 확인받는다. 시간은 mock 대신 `Clock` 빈과 공통 가짜 시계로 제어한다. Repository 테스트도 `@DataJpaTest` 대신 `IntegrationTestSupport`를 상속해 context를 재사용한다. → [무엇을 테스트할까](../../core/docs/TEST.md#무엇을-테스트할까), [시간 제어](../../core/docs/TEST.md#시간-제어), [Spring Context 재사용](../../core/docs/TEST.md#spring-context-재사용)
- **테스트 훅은 쓰기 전에 막는다(PreToolUse)**: `@DirtiesContext`, 직접 붙인 `@SpringBootTest`, 통합 테스트 클래스의 `@MockitoBean`만 검사한다. 클래스별 `@TestPropertySource`·`@ActiveProfiles`는 필요할 수 있어 검사하지 않는다. Bash로 쓴 파일은 검사하지 못해서 테스트 파일은 Write/Edit로만 쓰게 했다. → [`test-context-guard.py`](../../.claude/hooks/test-context-guard.py), [`core/CLAUDE.md`](../../core/CLAUDE.md)
- **`/pre-pr` stash 전에 staging 비우기**: 경로를 지정해도 `git stash`는 staging 영역 전체를 저장한다. 그래서 staging에 옛 버전이 있던 파일이 pop 때 커밋된 새 버전과 충돌했다. `git restore --staged .`를 먼저 하도록 고쳤다. → [`pre-pr/SKILL.md`](../../.claude/skills/pre-pr/SKILL.md)
- **개발일지는 PR과 함께 올린다**: main 직접 커밋 예외를 없애고, `/pre-pr`이 일지를 써서 같은 PR 브랜치에 커밋한다. 일지가 PR 내용과 같이 리뷰되고, main 직접 커밋이 사라진다. 같은 날 여러 PR에 같은 일지 파일이 올라가면 머지 때 충돌할 수 있어서, 나중에 머지하는 PR에서 합친다. → [`CLAUDE.md` 협업 흐름](../../CLAUDE.md#협업-흐름-2인), [`devlog/SKILL.md`](../../.claude/skills/devlog/SKILL.md)
- **한 파일에 작업 내용과 무관한 변경이 섞이면 파일 단위 stash로는 나눌 수 없다**: PR #3 때 `CLAUDE.md`·`.claude/README.md`·`SKILL.md`에 core 추가 작업이 섞여 있었다. 워킹트리 전체를 stash 하고 main 기준으로 이번 변경만 다시 적용해 커밋한 뒤 main에서 pop 했다. 스킬에는 아직 적지 않았다. (미반영)
